- **Who can reach it.** The chat's pages are in review, and `/api/ask` is not behind the release gate (`docs/methods/ask_limits.md`): a question sent to the route is answered.
- **What is kept of it.** A run file is in a public repository, so the results the tools should have held are not kept: in the stored runs every result read from a held or paused grid's own table is replaced by a note, and the figures of pj08's answer are struck out (`eval_site.py` `redact_held`, run before any grading). ## The spend guard (sessions 5262 and 5263)

- **The fault.** `warehouse/chat/eval/eval_s1113.py` `spent_today()` reads the day's spend of the evaluation's step from the site's cost ledger. It asked for the day in one request with `limit=5000`. Supabase answers a request with at most 1,000 rows, whatever limit it names. On 13 November the day held 1,092 rows, so the function counted 1,000 of them: USD 18.01 of USD 19.46.
- **What it guards.** The asking through the site's route (`eval_s1113.py --ask`, `run_eval.py`): the day's spend and a reserve must stay under `--cap` before each question. That asking was not run on 13 November.
- **What held on 13 November.** Every asking of this set went through the site's loop (`eval_site.py`), whose ceiling is counted on the session's own run file, not on the ledger. Each of the twelve askings ended under its USD 2. The run files hold USD 19.4570; the ledger, read whole, holds USD 19.4570 in 1,092 rows. No cap was passed and no call went unrecorded.
- **The fix** (session 5263). The ledger is read a page at a time in the order of its key, each page beginning after the last row read, until a page comes back empty; the server's exact count is then held against the rows read. A day that cannot be counted whole (fewer rows than the server counts, a page that does not move on, a call with no price) stops the asking before the call. It no longer falls back to a smaller number.
- **The same fault elsewhere: none.** The site's ceilings are sums the database makes (`site_ask_admit`, `internal_ask_spend`). The warehouse's own cap reads its ledger file whole (`warehouse/llm.py`). The thesis runner's is a sum in SQL. The daily cap of the scheduled steps reads Supabase's copy in pages of 1,000 (`warehouse/health.py` `ledger_remote`).
- **Added:** `eval_s1113.py --spent` prints the day's spend from the whole ledger (reads only). `eval_site.py --day-cap <USD>` holds every asking of the UTC day under one ceiling, read from the whole ledger before the asking: a chain's USD 20 is then counted by the ledger, not by adding run files.
- **Held by** `tests/test_session5263_ask.py`: a stand-in server with 1,092 rows that answers 1,000 at most, as Supabase does.
