## What is sound (no finding)

- **Row-level security is on for all 19 tables of schema `public`.** The anon key reads eight: `series`, `entities`, `events`, `latest_prices`, `catalogue`, `sources`, `headers` (rows whose license is public, by policy) and `game_scores`. The eleven internal tables have no select policy and no select privilege: each answered the anon key HTTP 401, Postgres code 42501. The proof asked for: `GET site_api_calls?select=*&limit=1` with the anon key answers 401, 42501.
- **No internal row is returned from a public table**: `catalogue`, `sources`, `headers` and `latest_prices` return no row whose license is not public; the cost ledger, the FERC contracts and the news stories return no row by name.
- **The private schema is closed**: `erw_private` (the secrets the functions compare against) gives the anon key no usage. Every function behind the internal token refused a wrong token (42501). Every function is `security definer` with a pinned `search_path`.
- **Storage**: `erw-archive` and `erw-thesis` are private. `erw-public` is public by design (the network page's hourly file). No storage policy exists, so the anon key can list and write nothing.
- **No secret in the git history.** Zero of the 12 values this machine uses appear in any commit of any branch. The pattern scan found 4 hits, all stand-ins in test scripts (`site/scripts/test-thesis-niche.mjs`, commit `f783854915`; `site/scripts/test-ask-speed.mjs`, commit `767ee96e69`): the literal words "a-stand-in-not-a-key" and "a-stand-in-token-of-...". No JWT, no Anthropic key, no GitHub token, no Resend key, no password in an address.
- **No secret in what a browser gets**: 0 hits in production's files and in the local build's. `SUPABASE_URL` and `SUPABASE_ANON_KEY` are server-side (no `NEXT_PUBLIC_` variable exists).
- **HTTPS**: `http://erw-flame.vercel.app/` answers 308 to `https://`, and every answer carries `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`. Nothing to add in code.
- **The spending routes already fail closed**: `/api/ask` asks the database before every question (`site_ask_admit`: the day's and month's ceilings, the visitor's daily number); `/api/thesis/run` and `/api/analysis` answer only the internal cookie and count the day's requests in the database.

## High

### H1. The internal token travels in addresses. `FIXED` (the old link kept), rotation `FOR SAMUEL`
- **What is exposed.** `/internal/unlock?token=<INTERNAL_COSTS_TOKEN>`, `/internal/costs?token=` and `/internal/ask?token=` put the one token that opens every review page, the Thesis Builder and the analysis queue into browser history, the host's request logs and anything that records an address. It is also the secret the database's internal functions check.
- **The fix.** `/internal/open` is a form that POSTs the token in the request's body to `/internal/unlock`, which sets the same two cookies. `/internal/costs`, `/internal/ask` and the new `/internal/usage` open with the internal cookie, so no address needs the token. Every `/internal` address is sent `Cache-Control: private, no-store`, `Referrer-Policy: no-referrer` and `X-Robots-Tag: noindex`. Ten wrong tries an hour from one address, then the form waits; a right token is never refused.
- **The risk of the fix.** None to access: the old link and the old `?token=` addresses work exactly as before (the GET handler is untouched), until Samuel confirms the form.
- **For Samuel.** (1) Confirm the form, then retire the GET link (delete the `GET` in `site/app/internal/unlock/route.ts` and the `token !== want` branch of the three internal pages). (2) Then rotate `INTERNAL_COSTS_TOKEN`: it has been in addresses and logs since session 67. Rotation means a new value in Vercel, in `.env`, in `site/.env.local`, and `python warehouse/supabase/apply.py` (the full run writes it to `erw_private.settings`; note that the full run stops at migration 014, so the one statement is run by hand). Every reviewer's cookie stops working at that moment and they unlock again. Not done here: it could lock the owner out.

### H2. Next.js 16.3.6 has six published advisories. `FIXED` (16.3.8)
- **What is exposed.** GHSA-3w37-wq28-93x7 (draft-mode content leaking into cached pages), GHSA-4jqv-mc3x-m676 and GHSA-mcj8-r9mp-w47p (cache poisoning of static and revalidated pages), GHSA-f87g-xv8r-7p7x (metadata image routes), GHSA-cjq9-62q9-8jv4 (request forgery in image optimization), GHSA-39w2-rjm5-chcv (the development server). All fixed in 16.3.8. The site uses no draft mode and no image optimization route; the cache-poisoning ones are written for self-hosted servers. The exposure on Vercel is low, but the version is the one thing an outsider can target without any key.
- **The fix.** `next` and `eslint-config-next` from 16.3.6 to 16.3.8 (a patch release published on 30 September 2026), then the build and every page check. `npm audit` afterwards lists only the linter's packages (L9).
- **The risk of the fix.** A patch release can still change rendering. The page checks decided: the build, `check-routes`, `check-values` and the browser checks pass on 16.3.8 (the session report lists each with its exit code). To go back: `npm install --save-exact next@16.3.6 eslint-config-next@16.3.6` in `site/`.

### H3. The anon key can write the cost ledger directly. `FOR SAMUEL`
- **What is exposed.** `site_api_calls` has an insert policy `with check (true)` for the anon key (migration 010): the site records its own model calls that way. Anyone holding the anon key can insert a row. One row with no price makes `site_ask_admit` answer "unpriced" and closes the question tools until a person deletes it; a row with a large price reaches the month's ceiling; any row falsifies `/internal/costs`. The anon key is not published today (it is server-side and in neither the history nor the bundle), but it is a public key by design and `package/README.md` tells a reader of the package to use one. **This is High the day the key is given to anyone, and Medium while it stays on the server.**
- **The fix.** A function `site_api_call_record(p_token, ...)` behind the internal token, `site/lib/chat/ledger.ts` calling it, then `drop policy anon_insert on public.site_api_calls` and the insert grant revoked. Same pattern as migration 028's functions.
- **The risk of the fix.** The ledger write's failure is swallowed by design: if the new write failed silently, spend would stop being counted and the ceilings would never trigger. It needs one real model call to prove, and this session's model spend is USD 0. Not done.

## Medium

### M1. The same class, three more places: the game's tables, the subscribers and the ask counter. `FOR SAMUEL`
- **What is exposed.** With the anon key alone: a row in `game_scores` with any score (the routes recompute every score from the moves; a direct insert skips that, so the leaderboard can be forged), rows in `game_plays` and unconfirmed rows in `subscribers` (no email is sent by a direct insert), and calls of `site_ask_admit` with invented visitors (20,000 of them make it answer "busy" and close the question tools for the day).
- **The fix.** Each write through a function behind the internal token; the three insert policies dropped; `site_ask_admit` given `p_token`.
- **The risk of the fix.** The site's code and the database must change in order (function first, site second, policy last), or the game and the sign-up stop storing. Best done as one landing with its own checks. Same condition as H3: only a holder of the anon key can do any of it.

### M2. Limits per address lived in each server instance's memory. `FIXED AFTER 028`
- **What is exposed.** The hourly limit of `/api/ask`, the game's 30 an hour and the sign-up had counts per instance: on Vercel each instance keeps its own, so the limit was a floor. `/api/download` (up to 200,000 rows a request) and `/api/thesis/pitchbook` had none.
- **The fix.** `site/lib/guard.ts`: `limited(req, bucket, limit, seconds)` counts in the database (`site_rate_admit`, migration 028) and in memory. Applied: ask 10 an hour, sign-up 5 an hour, game 30 an hour, download 60 an hour, PitchBook answers 60 an hour, wrong unlock tries 10 an hour. The database holds a keyed hash of the address for the day, never the address.
- **The risk of the fix.** One more database call on those routes (tens of milliseconds). If the database cannot be asked, the memory's count alone decides: exactly the behaviour before. A limit never fails closed.

### M3. The sign-up form could be used to send mail to addresses that did not ask. `FIXED` (the day's ceiling `FIXED AFTER 028`)
- **What is exposed.** `POST /api/subscribe` sends a confirmation email to any address typed, with no limit but a hidden field. A script could send confirmation mail to thousands of addresses from the ERW's sender: Resend's quota and the sender's reputation.
- **The fix.** Another site's form and a stock command-line client store and send nothing; five tries an hour per address; at most 200 confirmation emails a day in all (state "busy").
- **The risk of the fix.** A person behind a shared address who is the sixth to sign up in an hour is told to try later.

### M4. No security headers beyond the host's. `FIXED` (the full policy as report-only)
- **What is exposed.** No `X-Frame-Options` or `frame-ancestors` (a page could be framed by another site and clicked through), no `X-Content-Type-Options`, no `Referrer-Policy`, no `Permissions-Policy`, no Content-Security-Policy.
- **The fix.** `next.config.ts` sends all of them on every answer. The Content-Security-Policy that is **enforced** holds the four directives that cannot break a page: `base-uri 'self'; object-src 'none'; frame-ancestors 'none'; form-action 'self'`. The full policy (where scripts, styles, images and requests may come from) is sent as `Content-Security-Policy-Report-Only`.
- **The risk of the fix.** `X-Frame-Options: DENY` stops any other site, and any tool that shows the site inside a frame, from embedding a page. The report-only policy blocks nothing. `site/scripts/check-csp.mjs` opens every page of the release list in a real browser and lists what the full policy would block: on 10 October 2026, 82 pages, 0 violations on load (and the check first proves its detector by a script the policy does not allow). What a page does only after a click (a download, the 3D map's controls, a share card) is not proven, which is why the full policy is not enforced yet. To enforce it: move the report-only value to `Content-Security-Policy` once a week of use shows no violation in the console.

### M5. The chart library came from a public host with no integrity check. `FIXED`
- **What is exposed.** Every chart loads `echarts.min.js` from cdnjs (`site/components/echarts.ts`). If that file were ever changed at the host, the changed script would run on every page with a chart, with the page's full rights.
- **The fix.** `integrity` (the file's SHA-384, taken from the file as a page of the site received it: 1,034,102 bytes, `runs/session177/sri_echarts.out`) and `crossOrigin = "anonymous"` on the script element (`ECHARTS_SRI` in `site/components/echarts.ts`), so the browser refuses any other bytes.
- **The risk of the fix.** A wrong hash stops every chart, and so does a new version of the library without a new hash. Proven by a browser: `check-csp.mjs` opens `/storage` and fails unless the library loaded and a chart drew. The hash was computed here from the file received, not compared with a hash the host publishes (that would have been a request this session was not approved to make): worth one look by a person.

### M6. A new table is open to the anon key until someone closes it. `FOR SAMUEL` (two guards in place)
- **What is exposed.** Supabase's default privileges give `anon` and `authenticated` every privilege on any table, sequence or function `postgres` creates in schema `public`. Row-level security is what stands between a new table and the internet. It is on by convention (each migration says so) and by an event trigger read in the catalog: `ensure_rls`, on `ddl_command_end`, runs `public.rls_auto_enable()`, which turns row-level security on for a table as it is created (`runs/session177/catalog_read2.out`). With row-level security on and no policy a table is closed, so the default privileges alone open nothing today; they are one mistake away from it (a policy written too wide, the trigger dropped).
- **The fix.** So that a migration must grant what it means to, three statements (and their undo, the same with `grant` in place of `revoke ... from`):

  ```sql
  alter default privileges for role postgres in schema public revoke all on tables from anon, authenticated;
  alter default privileges for role postgres in schema public revoke all on sequences from anon, authenticated;
  alter default privileges for role postgres in schema public revoke execute on functions from public, anon, authenticated;
  ```

  They change nothing that exists: only what `postgres` creates afterwards.
- **The risk of the fix.** Any later migration that relies on the default (creates a table and a policy but no grant) would give a blocked table. It fails closed and is seen at once, but it changes the rules for every future session, so it is the owner's ruling. Meanwhile: migration 028 enables row-level security on any table of `public` that lacks it, and `verify_rls.py --catalog` fails on any table that is not in its expected list.

### M7. Python dependencies with advisories. `FOR SAMUEL` (nothing changed in `requirements.txt`)
- **What is exposed.** `pip-audit` on `requirements.txt` (120 packages resolved): `lxml` 5.4.0 (PYSEC-2026-87, entity resolution in the default parsers; fixed in 6.1.0), `cryptography` 46.0.7 (PYSEC-2026-3552, -3553, -3554 and GHSA-537c-gmf6-5ccf; fixed in 48.0.1 to 50.0.0), `setuptools` 78.1.1 (PYSEC-2026-3447; 83.0.0), `virtualenv` 20.39.1 (PYSEC-2026-4011 to -4014; 21.7.13). The ERW parses HTML and XML only from the publishers it names; `cryptography` is installed only as a dependency of other packages (no file of the ERW imports it), and its advisories concern certificate-chain checks and PKCS7 decryption, which the ERW's code does not call. `setuptools` and `virtualenv` are installation tools.
- **The fix.** Each needs a new major version. `lxml` is held at 5.x by `gridstatus==0.36.0` (`lxml~=5.3`); `requirements-py314.txt` already runs `lxml` 6.1.3 with `--no-deps`.
- **The risk of the fix.** A major version of a parser or of the crypto library under the daily run, on GitHub's runners. Not a change to make unattended.

### M8. A news feed or a model's words could put a script in a page. `FIXED`
- **What is exposed.** The digests, the Roundup, the method notes, the grid pages and the data standard are markdown written into the page as HTML (`site/lib/markdown.ts`, ten pages). The renderer passed raw HTML and any link scheme through. The method notes are the ERW's own, but the digest and the Roundup are written every day by a scheduled job from news feeds and a model's output and committed without a person reading them: a feed item carrying `<script>`, `<img onerror=...>` or a `javascript:` address, repeated by the model, would run in the browser of every reader of `/digest`, `/roundup` and the home page, with the reader's cookies for this site (the internal view's among them). The email already escaped the same text (`warehouse/news/email_digest.py`); the site did not. No such content was found in the 80 documents held.
- **The fix.** Raw HTML in a document is shown as the text it is, except the three forms the documents use (a comment, an `<a id>` anchor, a line break, subscript or superscript); a link or image may point to `http`, `https`, `mailto`, the site or the repository, and any other scheme goes nowhere.
- **The risk of the fix.** A document that relied on raw HTML would show the tags as text. None does: all 80 documents render with markdown's own tags only (`site/scripts/test-markdown-safe.mjs`). Two pages gain text, and it is a repair: `/data/methods/thesis` and `/data/methods/ercot_large_load_status` wrote placeholders in angle brackets (`<title> [<id>] ... <date>` and `in <month>`), which the browser took for tags. Read in a real browser before the fix (`runs/session177/stray_tags_before.out`): the Thesis Builder's note stopped at the word before `<title>`, and everything after it was hidden, the rest of the note and the page's footer included; the large-load note lost the word `<month>` twice. Both are now shown as written.
