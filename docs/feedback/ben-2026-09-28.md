# Notes on the ERW

Ben Domingue, 2026-09-28. Read against `SamuelEnrique/erw` at commit `ea77273`.

Samuel, a few notes after reading through the repository. Most of what I've written is about places where the IRW's architecture does not transfer cleanly to a live energy feed, plus a few things the IRW learned the hard way that seem likely to recur here. None of it is urgent except the two items marked **before the first release**.

## What carries over well

The governance documents came across intact and they are doing their job: `ARCHITECTURE.md` with its table of which document wins, `PRIORITIES.md` ranking kinds of work rather than tasks, the rule that nothing releases without a human, and an uploader that inherits `red_up`'s validator gate, true replace and `count(*)` proof. The data standard is a sensible adaptation. Three shapes (series, entities, events) rather than one `id, item, resp` is the right call for energy data, and interval-start UTC timestamps, a closed unit vocabulary and per-row provenance are all choices I would make again. I have little to add there.

## 1. The IRW's release model fits an archive; the ERW is mostly a feed

The IRW is a curated archive of finished datasets. A Redivis draft that a human reviews and releases every so often fits that well. The ERW is mostly a live feed, rewritten daily, and it currently uses the Redivis draft as its working state: the daily run restores the rolling-window tables from the draft (`upload.py --restore`), merges new days in, and uploads them back (`warehouse/run_daily.sh`, `restore_before_run` in `warehouse/redivis/config.yaml`).

Two consequences follow. First, no version has been released, so nothing is citable yet (your `docs/platform-tools.md` says as much under tool 15). Second, and more important, the unreleased draft is the only copy of the history those tables have accumulated: the ISO price windows, the `*_trader_daily` tables, weather, `policy_actions` and the rest of the restore list. A draft is a scratch space; it should not be the only place anything lives.

My suggestion is to separate the working store from the citable archive. For example: append-only, immutable partitions (say, one file per table per month) kept somewhere durable, with a Redivis release on a fixed cadence (monthly seems about right) as the thing people cite. The daily rewrite then never touches anything that isn't recoverable.

## 2. Silent history loss (before the first release)

This is a specific consequence of (1), inherited from `red_up`. `push()` in `warehouse/redivis/upload.py` deletes the draft table before recreating and uploading it. In the IRW we have seen transient Redivis SDK errors (an `AttributeError: 'NoneType' object has no attribute 'get'` that hides a 5xx or throttling response) land after the delete, leaving the table gone from the draft. In the IRW that is a hole we can refill from the released version. Here, consider what happens the next day:

1. `restore()` iterates `ds.list_tables()` and fetches the rolling tables it finds. A missing table is simply not restored, with no error.
2. The connector writes its usual three-day window to a fresh file.
3. `--changed` sees a new hash and uploads it as the whole table.
4. The `count(*)` check passes, since the draft matches the (short) CSV.

The accumulated history is gone, with no backup and no failure anywhere in the log. Two small gates would stop the class: `--restore` should fail if any table that `redivis_uploads.csv` lists and the restore patterns match is absent from the draft; and the uploader should refuse to shrink a rolling-window table below the row count it last recorded for it. Relatedly, in the IRW the Python client's `list_tables()` silently under-reported a large dataset by about half. At 112 tables you are probably fine, but it is not something to lean on for an existence check.

## 3. Internal tables go to the same Redivis dataset (before the first release)

`upload.py` uploads every table in `warehouse/output/`, including those `coverage.csv` marks `internal`: PJM capacity, CARB and RGGI auctions, the IMF series via FRED, PortWatch, `news_stories` with third-party text, and the `*_evidence` tables. The license is written into the table description but nothing filters on it. As far as I know, Redivis access is set per dataset rather than per table, so the first release of a public `energy_research_warehouse` would redistribute data you have yourself recorded as not redistributable. The internal tables need their own restricted dataset, and the uploader should route by license.

## 4. Ownership

The dataset is owned by a personal user account (`owner_kind: user` in `config.yaml`). We moved IRW ownership once and it was not free. Given that the ERW is an independent study with an end date, moving it under an organization now, while it is small, is much cheaper than later.

## 5. Table granularity and the 1,000-table cap

One table per ERCOT year, one per ISO for EIA-930, one per ISO for the trader view: the count is 112 after four days. Redivis caps a dataset at 1,000 tables, and the IRW hit that cap and now spreads across several datasets, which complicates everything downstream (listing, fetching, citing). Your standard already carries `entity`, `market` and `geo`, so fewer, longer tables (all ISOs' EIA-930 demand in one table, all ERCOT years in one table) cost you nothing in expressiveness and put the cap far away.

## 6. Model-extracted rows sit beside source-published rows

`energy_deals`, `datacenter_projects`, `datacenter_facilities`, `policy_reads` and `energy_companies` are produced by a model reading text, and they are `public` tables with the same standing as EIA prices. Your own spot checks are useful here: 0.95 of deal fields correct, 59 of 62 policy-read fields, and 7 of 10 Thesis Builder capital rows fully supported. Those are fairly good numbers for extraction; they are not the numbers of a source record. The IRW handles this with tiers for its derived layer, so a user can tell what a publisher said from what we inferred. I'd add something similar: a column or a table-level flag distinguishing source-published from model-extracted rows, so a user citing a number knows which kind it is. `energy_companies` also merits a look on the rights side, given that it comes from web search.

## 7. Scope, relative to your own PRIORITIES.md

I raise this one more gently, since it is your project. The "Not now" list in `PRIORITIES.md` rules out scores and derived indicators inside the warehouse, a custom UI, and adding sources faster than they can be validated. Since then the ERW has added news scoring, a newsletter with subscribers, a Thesis Builder for investors, and a plan for 31 tools (including a meme generator). Meanwhile, the GitHub run on 09-27 had 32 failed tables, and all six `*_trader_daily` tables are failing on the same dtype merge error. The IRW's experience is that the warehouse's value is almost entirely trust, and that everything built on top inherits whatever is wrong underneath. I'd either revise the "Not now" list to match what you are actually doing, or hold the platform tools until the warehouse layer is steady. Either is defensible; the current mismatch between the document and the work is not.

## Smaller things

- About 50 `SESSION_*_PROMPT.md` / `SESSION_*_REPORT.md` files sit at the root. An `archive/sessions/` folder (your own `ARCHITECTURE.md` section 3 suggests this) would make the root readable.
- 38 MB of screenshots are committed under `site/screenshots/`, and `.git` is already 163 MB. Screenshots regenerated every session will grow that quickly; they probably belong outside git.
- `CLAUDE.md` says "do not push unless a human asks", while the daily workflow commits and pushes metadata. Probably fine, but worth reconciling in the text.

If it is useful, I'm happy to turn items 2 and 3 into issues on the repo, since those are the two that need to land before anyone clicks release.
