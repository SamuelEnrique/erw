## Root causes

Written by session 377 (20 October 2026) from the sessions' reports, `docs/state/scheduled_failures_2026-10-12.md` (session 202) and git; one paragraph a cause, in the order the failures above first show it. `warehouse/health.py summary` keeps this section when it writes the file again.

**carb_lcfs (HTTP 202 from ww2.arb.ca.gov; on 9 October also its 3-run streak row).** CARB's host answers GitHub's runners HTTP 202 with no body; from a residential connection the file downloads. The publisher's side, not the ERW's code. Session 166 D recorded it as a known gap (`known_gaps.csv`, decided by Samuel on 8 October), but the step still recorded a failure; session 206 (`76f9f9ec`, narrowed in `c7ae28e3`) records a known gap on the runner as a skip and pulls the table daily on the data machine (`dm_carb_lcfs`); session 271 (`ffd02d28`) made a publisher's lag on the data machine "stale at source", a skip. No failed row after 12 October.

**board_page, FileNotFoundError for carb_lcfs_credit_prices.csv.** `build_lcfs` in `price_board.py` read CARB's table without asking whether it exists, and on the runner it never does (above); the runner had not rebuilt `board.json` since 6 October. Fixed by session 202 (`f4d85e77`): the two LCFS rows are left out when the file is absent and the held rows kept.

**policy_monitor_refresh (Texas HTTP 403, Pennsylvania ConnectTimeout, Oregon ConnectionError).** The regulators' hosts did not answer the runner (11 October was a bad network day for the runner: SPP's portal failed too); Texas and Pennsylvania failed that day only, Oregon's docket host two days running, and one regulator failing marked the whole step failed. Fixed by session 206 (`76f9f9ec`): `policy_monitor_refresh:orpuc` is a known gap, skipped on the runner and pulled daily on the data machine (`dm_orpuc_dockets`); nothing changed for Texas or Pennsylvania, which did not fail again.

**supabase_load, api_cost_ledger (and the Roundup's "ledger: live set ... refused, older than the live copy" of 11 October).** Each machine appends to its own copy of the ledger; the runner restored its copy from the Redivis draft (its own calls only), and `warehouse/supabase/load.py` replaced the whole table but refused one with fewer rows than Supabase, which held the old laptop's 3,179 rows. Diagnosed by session 176 (`f52e8ec0`, a repair not then run). Fixed by session 206 (`a3cee0c5`): `union_by_key` in `live_set.yaml` loads the ledger by `event_id`, with no older-than-live guard; session 176's repair was then run (3,519 rows in all four places). Not seen since.

**Package tests, test_large_table_by_partition[ercot_dam_esr_awards].** A table the runner rebuilds from the archive gets `warehouse/archive/restore.py`'s note ("Rebuilt from the ERW archive...") as its first header line, and the test (`package/tests/test_erw.py`) required that line to begin "Energy Research Warehouse (ERW):". Session 166 read it as this table being behind the cloud's copy, which was wrong; session 202 found the cause. The row names one test only because `warehouse/health.py` `reason_of` keeps the last error line: two to nine other failing tests hid behind it each day, and session 202 fixed those too. Fixed by session 202 (`f4d85e77`): the tests read past the note. The same fault came back on 20 October in another form (session 336, below).
